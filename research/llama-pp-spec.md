# llama.cpp CPU speedups — 1.7B Q4_K_M on an 8-thread laptop (no GPU)

Target: `llama-server` b12686 (2026), dense ~1.7B Q4_K_M, 8 threads, CPU-only.
"pp" = prompt processing (prefill), "tg" = token generation (decode).
All gains are CPU-only, single-user unless noted. Figures are order-of-magnitude; verify with `llama-bench` / `llama-perf` on your own box.

Docs: only helps batch sizes > 32. | Must compile yourself + install `libopenblas-dev`; no decode benefit; occasional numerical drift. | `cmake -B build -DGGML_BLAS=ON -DGGML_BLAS_VENDOR=OpenBLAS` | https://github.com/ggml-org/llama.cpp/blob/master/docs/build.md |

| **`-t` threads (generation)** | Threads for decode. On 8 logical cores use 8; more than physical cores oversubscribes and *lowers* tg. | tg scales up to #physical cores, then flat/regresses. | >physical cores hurts; hyperthread siblings contend. | `-t 8` | https://docs.jan.ai/desktop/local-engine/llama-cpp |
| **`-tb` threads-batch (pp)** | Threads for prefill/batch. Set equal to `-t` (8) to max pp; pp is the phase that benefits from all cores. | pp near-linear to core count. | Oversubscription (tb≫cores) thrashes; keep `-tb ≤` logical cores. | `-tb 8` | https://github.com/ggml-org/llama.cpp/discussions/26667 |
| **`-b` batch-size (ubatch cap)** | Logical batch (tokens) per prefill chunk. Larger = better pp throughput up to ubatch limit. Default 2048. | Larger `-b` raises pp t/s (more work per BLAS call). | Diminishing returns past ubatch; big `-b` raises memory. | `-b 2048` | https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md |
| **`-ub` ubatch-size (physical)** | Physical micro-batch actually computed. **Key pp knob.** 512 default; raising to 1024–2048 speeds pp on CPU+BLAS. | pp **+20–50%** going 512→1024/2048 on CPU. | Must be ≤ `-b`; too large hurts cache / latency on small prompts. | `-ub 1024` (or 2048) | https://github.com/ggml-org/llama.cpp/discussions/18308 |
| **`--spec-type ngram-simple`** | Draftless self-speculation: find last matching n-gram in history, draft the following m tokens, verify in one batch. No draft model. | tg **~1.3–2×** on repetitive/structured output (JSON, tool calls, code, reformatting). Near 0 on diverse prose. | Pessimization on low-repetition text (draft overhead > accepts); costs a little VRAM/RAM. | `--spec-type ngram-simple --spec-draft-n-max 64` | https://github.com/ggml-org/llama.cpp/blob/master/docs/speculative.md |
| **ngram-simple tuning (size-n / size-m / min-hits)** | `size-n`=lookup length (def 12), `size-m`=draft length (def 48), `min-hits`=min occurrences (def 1). For JSON/tool schema: keep n≈8–12, m≈16–32, min-hits 1–2. | Larger m = more speedup *if* accepted; wrong m lowers acceptance. | m too big → low accept → pessimization; small n over-matches. | `--spec-ngram-simple-size-n 12 --spec-ngram-simple-size-m 32 --spec-ngram-simple-min-hits 1` | https://github.com/ggml-org/llama.cpp/blob/master/docs/speculative.md |
| **ngram-mod (alternative)** | LCG hash pool (~16 MB, constant mem), shared across slots, variable draft length. Good for code blocks / reasoning repeats / summarization. | tg **~1.3–1.8×** on iterative/structured text. | Small n not recommended; MoE needs long drafts; dense can lower n-min. | `--spec-type ngram-mod --spec-ngram-mod-n-match 24 --spec-ngram-mod-n-min 48 --spec-ngram-mod-n-max 64` | https://github.com/ggml-org/llama.cpp/blob/master/docs/speculative.md |
| **ngram-cache** | Keeps n-gram statistics (optionally loaded from file) to draft. | Modest tg gain on repeated corpora. | Extra state; benefit only with repetition. | `--spec-type ngram-cache` | https://github.com/ggml-org/llama.cpp/blob/master/docs/speculative.md |
| **`--cont-batching`** | Continuous batching: slots pack requests dynamically. | **Single user: ~no change** (one stream). Helps only with `--parallel N`>1 concurrency. | Slight overhead; no single-user throughput gain. | `--cont-batching` | https://github.com/ggml-org/llama.cpp/discussions/18308 |
| **`--parallel N` (slots)** | Number of KV-cache slots. | **Single user: keep N=1.** N>1 splits ctx & KV across slots and *lowers* single-stream tg. | N>1 only helps many concurrent clients; wastes KV per slot. | `--parallel 1` | https://github.com/ggml-org/llama.cpp/discussions/18308 |
| **`--no-warmup`** | Skip the empty warmup run at startup. | Faster **startup** only; no steady-state pp/tg change. | First real request may pay warmup cost (one-time). | `--no-warmup` | https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md |
| **`--mlock` / mmap (load mode)** | mlock pins weights in RAM (no page-out); mmap (default) lazily maps. `LLAMA_ARG_LOAD_MODE=mmap+mlock`. | mlock avoids first-token stalls from page faults if RAM is tight; mmap = lower RAM, lazy load. | mlock needs RAM ≥ model; can OOM. mmap may stall on cold reads. | `--mlock` (or default mmap) | https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md |
| **`-cram` / `--cache-ram`** | Max prompt-cache RAM in MiB (default 8192; -1 unlimited, 0 disable). | Larger = more prompts cached → skip re-prefill on repeated prefixes (big pp win on chat/tool loops). | Uses RAM; default 8 GiB may be too high on a laptop — lower it. | `-cram 2048` | https://github.com/ggml-org/llama.cpp/pull/16391 |
| **`--prio` / `--prio-batch`** | Thread/process priority 0 normal,1 medium,2 high,3 realtime. | `--prio-batch 1–2` can lift pp when desktop load competes. | Realtime (3) can starve the desktop; avoid on a laptop. | `--prio-batch 1` | https://github.com/ggml-org/llama.cpp/blob/master/tools/cli/README.md |
| **`--poll` / `--poll-batch`** | Polling level (busy-wait) for work; llama-bench default 50. | Higher poll = lower latency, more CPU burn; 0 = sleep (cool). | High poll on battery/thermal laptop wastes power; keep moderate. | `--poll 50` | https://github.com/ggml-org/llama.cpp/blob/master/tools/llama-bench/README.md |
| **ZenDNN backend** | AMD EPYC/CPU deep-learning primitives (`-DGGML_ZENDNN=ON`). | Big pp/tg gains **on AMD Zen** CPUs. | **Not for Intel ThinkPad** — skip. | `-DGGML_ZENDNN=ON` | https://github.com/ggml-org/llama.cpp/blob/master/docs/build.md |

## Top 5 to apply now

1. **Build with OpenBLAS (or oneMKL on Intel) yourself** — the prebuilt ubuntu-x64 tarball has no BLAS. Biggest pp win (~2–3×); zero effect on decode. `cmake -B build -DGGML_BLAS=ON -DGGML_BLAS_VENDOR=OpenBLAS`. (build.md; release.yml)
2. **`-t 8 -tb 8 -b 2048 -ub 1024`** — match threads to the 8 logical cores and raise ubatch for prefill throughput; do not exceed physical/logical cores (oversubscription regresses). (discussions/26667, 18308)
3. **`--spec-type ngram-simple --spec-draft-n-max 64 --spec-ngram-simple-size-m 32`** for JSON/tool/code/reformatting turns — ~1.3–2× tg there; **leave it off** for diverse prose (pessimization). (speculative.md)
4. **`--parallel 1` and skip `--cont-batching`** for a single user — extra slots/continuous batching only help concurrency and *hurt* single-stream tg. (discussions/18308)
5. **`-cram 2048` (not the 8 GiB default) + default mmap**, add `--no-warmup` for faster startup, and `--prio-batch 1` if the desktop competes — keeps RAM/latency sane on a laptop. (PR 16391; server/cli README)

Notes: `--poll` defaults moderate (50 in llama-bench); keep it there on battery. ZenDNN is AMD-only — ignore on a ThinkPad; the Intel path is oneMKL/OpenVINO. NUMA is irrelevant on a single-socket laptop. Always confirm deltas with `llama-bench -m model.gguf -p 512 -n 128` before/after each change.
